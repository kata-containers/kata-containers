# 上游待决问题：实测证据与建议回答

本文把 PR 评审中悬而未决的问题逐条列出，并给出**本次实测得到的硬证据**，以及据此可以给出的回答。凡是"实测"的都注明了证据出处（§ 指向 `可组合Guest镜像AppArmor实施方案.md`）。

---

## Summary (EN)

Testing a real pod with `localhost/kata-apparmor-test` on a kata runtime class produced evidence for the open semantic questions:

1. **The name is resolved twice, in two different namespaces.** containerd validates it against the *host's* AppArmor profiles while generating the OCI spec, and the guest agent separately loads it from the extension image. With no host-side profile the container is refused outright (`apparmor profile not found`); with one, the guest profile is what actually confines the process. The two need not match, and nothing in the API expresses the difference.
2. **Omitting the extension fails closed, which is right**, but a *mistyped path* is silently skipped: the runtime emits no kernel parameter at all, so the guest looks like one with no extensions configured. The user sees policy simply not applying.
3. **The exec path must keep the profile.** The agent selects it before `execve`, and this PR fixes a place in runtime-rs that cleared it. Verified for the container process; a dedicated `ExecProcess` case is not yet covered.
4. **A ready-made default profile is a trap.** Ours is deliberately permissive yet still refuses harmless binaries, because its exec rules cannot know the real container root. A default shipped on the same basis would break working workloads.

Everything below gives the commands, observed output, and what remains unverified.

## 问题 1（最关键）：K8s 的 AppArmor API 语义

### 问题原文
Kubernetes 的 AppArmor API 用 `RuntimeDefault` / `Localhost/<name>` 表达 profile。在本方案里，**这个 `<name>` 指的是宿主机的 profile，还是 guest 内的 profile？**

### 实测证据（本次最重要的发现）

用带注解的 pod 实测（`container.apparmor.security.beta.kubernetes.io/app: localhost/kata-apparmor-test`，`runtimeClassName: kata`），观察到 **profile 在两侧各被解析一次，且两侧互相独立**：

| 环节 | 谁在解析 | 解析到哪 | 证据 |
| --- | --- | --- | --- |
| 1 | **宿主机 containerd**，生成 OCI spec 时 | 宿主机 `/etc/apparmor.d/` | 宿主机上**没有**该 profile 时，容器创建直接失败：<br>`failed to get container spec opts: failed to generate apparmor spec opts: apparmor profile not found kata-apparmor-test` |
| 2 | **guest 内 kata-agent** | guest 的 extension 镜像 | agent 从 `/run/kata-extensions/apparmor/profiles/<name>` 加载并施加；`PROFILE=[kata-apparmor-test (enforce)]` |

**两侧的 profile 内容可以完全不同，而 API 层没有任何手段表达这个区别。** 实测中宿主机那份 profile 纯粹是为了满足 containerd 的校验而存在——真正约束容器进程的是 guest 那份（因为 OCI 容器跑在 VM 里，宿主机的 AppArmor 对它没有作用）。

### 建议回答

**同一个名字现在必须同时存在于两个命名空间，而两者语义不同。** 这有三个后果，需要在文档/设计里写清，否则用户会误解：

1. **用户的直觉会是错的**。K8s 用户按 `Localhost` 的既有语义，会认为"我在节点上加载了 profile，容器就受它约束"。在 Kata 下**不是这样**——节点上那份只用于通过校验，真正生效的是 guest 里那份。用户若只加载了节点侧，会得到一个"通过校验但实际 unconfined"的容器。
2. **存在同名不同义的风险**。宿主机和 guest 各有一份 `kata-apparmor-test` 时，两者内容可以不一致，而 API 无法表达。建议要么规定"guest 侧为准、宿主侧仅为占位符"，要么在文档中明确要求两侧同源。
3. **`RuntimeDefault` 需要单独定义**。Kata 的 `RuntimeDefault` 应当是**guest 的**默认 profile，而不是宿主机的 `docker-default` 之类。这一点需要明确，否则 `RuntimeDefault` 在 Kata 下会指向一个语义不同的东西。

**实测还说明：本方案的 fail-closed 行为是正确的选择。** guest 侧拿不到 profile 时，agent 拒绝创建容器（`exitCode 128` + 明确错误），而不是静默以 `unconfined` 放行——这正好避免了上面第 1 点的坑。

## 问题 2：extension 是否应当默认挂载

### 问题原文
`guest_extension_images` 应该默认配置好（开箱即用），还是保持可选（用户显式配置）？

### 实测证据

- 配置里**没有** `guest_extension_images` 时：guest 不挂载任何 extension，kernel cmdline 里没有 `kata.extension.*`，agent 的 `extension_is_configured()` 判定为"未配置"，**请求 profile 的容器创建失败**（§13.9.6）。
- 配置里**有**该段时：正常挂载并施加策略（§13.9.8）。
- 配置里**路径指向不存在的文件**时：runtime **直接跳过该 extension**，既不 emit 内核参数也不挂设备，guest 表现为"没配置任何 extension"（§13.9.9）。这是合理的防御行为，但意味着配置写错时**不会报错**，只会表现为"策略没生效"。

### 建议回答

**保持可选，但需要让"配置写错"可诊断。** 当前的风险是：路径写错 → 静默跳过 → 用户以为扩展已生效 → 实际容器 unconfined。这与问题 1 第 1 点是同一类坑。

可选做法（按代价从小到大）：
- 文档里明确"路径不存在时会被静默跳过"；
- 或让 runtime 在路径不存在时**告警**（而非静默跳过）；
- 或在 agent 侧增强 `extension_is_configured()` 的判据——目前它只看 cmdline，看不出"配置了但跳过"和"根本没配置"的区别。

另外，extension 默认挂载会带来**额外一块 virtio-blk 设备和一次挂载**，是否可接受由维护者判断；本次实测中它工作正常。

## 问题 3：ExecProcess 时 profile 的继承与拒绝

### 问题原文
`ExecProcess`（`kubectl exec` / `ctr task exec`）时，容器已有的 AppArmor profile 应当被继承，还是应当拒绝？

### 实测证据

- **agent 侧**：`container.rs` 在起容器进程前调用 `prepare_profile()`，在 `execve` 前调用 `select_profile()`（`container.rs:419` / `:686`），因此 exec 出来的进程**会**被施加同一个 profile。
- **runtime-rs 侧**：提交 #6 修掉了一处会在 exec 路径上**清掉** profile 的代码（`manager.rs` 中原来的 `oci_process.set_apparmor_profile(None);`），改为把 profile 作为不透明值保留。
- **Go runtime 侧**：`Process.ApparmorProfile` 是协议里的既有标准字段（`src/libs/protocols/protos/oci.proto:73`），Go runtime 通过 OCI spec → agent proto 的常规转换传递，无需额外代码。
- **实测中观察到的间接证据**：容器进程与 PID 1 都被约束（`PROC1=[kata-apparmor-test (enforce)]`），说明施加发生在进程树根部。

### 建议回答

**应当继承，且本 PR 已修好。** 保留 profile 是正确方向：清掉它会让 `kubectl exec` 成为一个**逃逸口**——攻击者只需 exec 一次就脱离约束。

需要补充说明的是：**这条路径的实测还不完整**。本次验证的是"容器主进程被约束"，**没有**单独测 `ExecProcess` 起的进程（例如在 pod 里 `kubectl exec` 再读一次 `attr/current`）。建议在 PR 描述里把这一点列为"已验证设计、待补用例"，或由维护者决定是否要求先补测试。

## 问题 4：生产是否需要 `kata-default` profile

### 问题原文
除了测试用的 profile，是否需要提供一个生产级的默认 profile（`kata-default`）？

### 实测证据

- 本 PR **故意不提供**默认 profile。理由写在测试 profile 自己的注释里：
  > It exists to prove the mechanism end to end inside a guest... A production default profile would have to start from a real guest file tree and a real workload's access needs, and be reviewed as such.
- 实测**印证了这个理由**：测试 profile 的 `mr` 规则只覆盖 `/bin/**`、`/usr/bin/**` 等，而真实容器根里还有别的路径，结果导致 `uname`、`grep`、`tail`、`sleep` 等外部二进制**被拒绝**（`exitCode 126`）。容器能起来，但很多命令跑不了。

### 建议回答

**暂不提供，且本次实测说明"随手写一个默认 profile"是有害的。** 实测中那个 profile 已经写得很宽松（几乎只 deny 一个路径），仍然因为**没有覆盖真实文件树**而把无害命令拒掉。一个被当作"默认值"广泛启用的 profile，若基于同样的猜测，会把大量正常负载打挂。

如果上游坚持要一个默认值，建议它：
- 从**真实 guest 文件树**导出（例如用 `aa-logprof` 或先以 complain 模式收集访问）；
- 明确定位为"基线 + 可叠加"，而不是"开箱即用且无需调整"；
- 单独评审，不并入本 PR。

## 问题 5：宿主 vs guest profile 的区分（与问题 1 同源）

已在问题 1 中给出实测证据。这里补充一点实现层面的观察：

本 PR 的 agent 侧用 `PROFILE_FILE_PREFIX = "localhost/"` 解析 OCI 名（把 CRI 的 `localhost/<name>` 剥成 `<name>`，再到 extension 里找 `profiles/<name>`）。这个映射是**必要且正确的**，但它也恰好说明了问题所在：**API 的 `localhost/` 前缀在 Kata 下无法区分"宿主 localhost"与"guest localhost"**，而两者是不同的命名空间。

## 问题 6：签名与回滚格式

本 PR 未涉及。当前 extension 支持两种形态，实测确认了它们的行为差异（§13.9.3 / §13.9.10）：

| 形态 | 布局 | 行为 |
| --- | --- | --- |
| unmeasured | 仅 p1（data） | 直接挂载（`verity_params` 为空） |
| measured | p1（data）+ p2（hash） | `veritysetup open` 验证；**root_hash 不匹配即拒绝挂载并关机** |

实测把 measured 镜像的 `root_hash` 改坏一位后，guest **拒绝挂载 → systemd `OnFailure=poweroff.target` → agent 从未启动 → sandbox 创建失败**（§13.9.10）。也就是说**fail-closed 已经成立**，签名/回滚是它之上的一层。建议把"签名格式"作为独立议题，本 PR 不阻塞。
