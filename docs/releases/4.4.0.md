# Kata Containers 4.4.0

4.4.0 is a minor release following [4.3.1](4.3.1.md). It adds a dedicated
Substrate guest archive, raises the Cloud Hypervisor CPU ceiling on x86_64,
and improves container cleanup, VM restore and multi-layer EROFS support.
This document covers only
[`03cf2ec06a5d302f23af811744f6bcea49988bfb..44e886fa1ca02149a87202f0c6972114482baf86`](https://github.com/kata-containers/kata-containers/compare/03cf2ec06a5d302f23af811744f6bcea49988bfb...44e886fa1ca02149a87202f0c6972114482baf86).

!!! warning "Review compatibility before upgrading"
    The supported containerd minimum moves to 2.3. `kata-manager` no longer
    installs or manages Kata. Custom virtio-blk rootfs images need usable
    partition identities, and container removal no longer honors the former
    agent request timeout.

## New features

### A dedicated Substrate guest archive

Substrate users can obtain a Debian `trixie-slim` guest and the standard Kata
kernel without downloading Kata's host binaries. The amd64 and arm64 build
and release definitions produce
`kata-static-substrate-VERSION-ARCH.tar.zst`; the Substrate components are
excluded from the other release archives and `kata-deploy` downloads
([#14223](https://github.com/kata-containers/kata-containers/pull/14223),
[Substrate #1967](https://github.com/agent-substrate/substrate/pull/1967)).

The guest runs a dedicated GNU libc agent as PID 1, with seccomp enabled and
agent policy, init-data and dm-verity support disabled. Its ext4 image is
packed in userspace without loop devices or privileged containers, with the
alignment required for Substrate's PMEM/DAX mounts. It retains package
metadata for inspection and vulnerability scanning. The builder resolves the
Debian base image digest before checking the cache, so a refreshed base causes
a rebuild; apt package versions can also change between builds.

Build the complete guest archive with `make kata-static-substrate-tarball`,
or just the rootfs with `make rootfs-image-substrate-tarball`. Substrate
supplies Cloud Hypervisor, `virtiofsd` and the other host dependencies.

This is a specialized guest: it omits general-purpose guest tools such as
iptables and `mkfs.ext4`, and has no chrony service. Its VMM must correct the
clock on restore. Create fresh snapshots when changing the guest image.
The upstream boot experiments do not establish steady-state performance
gains for this build. See the [image builder guide](../../tools/osbuilder/README.md#substrate-image)
and [agent build notes](../../tools/packaging/static-build/agent/README.md).

### Cloud Hypervisor supports up to 512 vCPUs on x86_64 KVM

Both runtimes now allow Cloud Hypervisor guests with up to 512 vCPUs on x86_64
KVM, and the x86_64 guest kernel is built with `CONFIG_NR_CPUS=512`
([#13811](https://github.com/kata-containers/kata-containers/pull/13811)).
MSHV and other architectures retain the 256-vCPU Cloud Hypervisor ceiling.
Other hypervisors keep their existing limits.

Review `default_vcpus` and `default_maxvcpus` when sizing a guest; the larger
ceiling does not change host CPU caps applied during configuration adjustment.
Rust validation rejects fractional boot requests above the ceiling, such as
512.5. Resize requests are capped at the configured maximum.

## Breaking changes

### The supported containerd baseline moves to 2.3

The minimum containerd version in `versions.yaml` moves from `v2.2` to
`v2.3`; the latest test selection remains `v2.4`
([#14183](https://github.com/kata-containers/kata-containers/pull/14183)).
Upgrade hosts still using containerd 2.2 before adopting this baseline.
Updating Kata does not update the host containerd daemon.

### kata-manager is retired

`utils/kata-manager.sh` now prints a retirement notice and exits with status 1
for every invocation. Its former installation, version-listing and
configuration-switching operations no longer run
([#14265](https://github.com/kata-containers/kata-containers/pull/14265)).
Replace automation that invokes it with a supported method from the
[installation guide](../installation.md), and manage runtime configuration
through that deployment method.

### Custom virtio-blk rootfs images require partition identities

The Rust QEMU, Cloud Hypervisor and Dragonball backends select virtio-blk
rootfs partitions by `PARTUUID`, avoiding accidental boots from an extension
disk when asynchronous probing assigns it `/dev/vda`
([#14161](https://github.com/kata-containers/kata-containers/pull/14161),
[#14154](https://github.com/kata-containers/kata-containers/issues/14154)).

Custom images must have a readable DOS or GPT partition table with the root
filesystem in partition 1. DOS images need a nonzero disk signature; GPT
images use partition GUIDs. Measured images also need hash partition 2.
Keep rootfs and extension partition identities distinct. Images that lack the
required identities now fail before VM startup, so check custom images before
rolling out the new runtime.

Unmeasured boot uses `rootwait`; dm-verity boot selects both backing partitions
by identity and waits through `dm-mod.waitfor`. Initrd and pmem boot paths
retain their existing selection. See [Composable VM images](../design/composable-vm-images.md).

### Container removal waits for agent cleanup

The agent completes `RemoveContainerRequest` synchronously instead of
returning on its former `timeout`. The protocol reserves the removed field's
number and name, and `runtime-rs` no longer sends it
([#14146](https://github.com/kata-containers/kata-containers/pull/14146),
[#13920](https://github.com/kata-containers/kata-containers/issues/13920)).

Custom agent clients must regenerate bindings and stop setting that field.
An older client's timeout value no longer bounds agent cleanup. Review
callers that relied on an early response: removal now waits for destruction
and resource cleanup, avoiding work left running after a timeout and
inconsistent agent policy state.

### Masked directories and process limits take effect

The agent now hides directories listed in OCI `maskedPaths` behind an empty
read-only tmpfs. Previously, attempting to bind `/dev/null` over a directory
could leave it visible. This affects paths such as `/sys/firmware` and
`/proc/acpi`. Masks share one tmpfs, retain SELinux mount labeling and work
when a child path appears before its parent
([#14189](https://github.com/kata-containers/kata-containers/pull/14189),
[#14188](https://github.com/kata-containers/kata-containers/issues/14188)).

Workloads that depended on reading a masked directory need their OCI masking
requirements reviewed. The IBM Secure Execution test uses a privileged pod
to inspect guest firmware state; that test adjustment is not a recommendation
to make application pods privileged
([#14213](https://github.com/kata-containers/kata-containers/pull/14213)).

The shared protocol conversion also preserves supplied PID limits instead of
dropping them, allowing the agent to apply them to container cgroups
([#14141](https://github.com/kata-containers/kata-containers/pull/14141)).
Review configured limits if workloads previously exceeded them: process
creation can now fail at the intended limit.

## Notable fixes

### Runtime lifecycle and devices

- **Failed sandbox starts can be retried.** `runtime-rs` removes abandoned shim
  sockets when no process accepts connections, removes its own socket on exit,
  and uses a `cgroups-rs` update that handles leftover systemd units
  ([#14128](https://github.com/kata-containers/kata-containers/pull/14128),
  [#14103](https://github.com/kata-containers/kata-containers/issues/14103)).
  A further update fixes missed systemd completion signals with dbus-broker,
  which could prevent sandbox startup after a 30-second wait on Rocky Linux
  10.2 ([#14261](https://github.com/kata-containers/kata-containers/pull/14261),
  [cgroups-rs #182](https://github.com/kata-containers/cgroups-rs/pull/182)).
- **Failed VMM starts leave enough state for cleanup.** The Rust runtime records
  the spawned VMM's identity before propagating a startup error, allowing
  teardown to confirm its exit and release resources such as `virtiofsd`,
  temporary rootless users and runtime directories
  ([#14143](https://github.com/kata-containers/kata-containers/pull/14143)).
- **Recovery uses the sandbox's own configuration.** The runtime records its
  configuration path in `/run/kata/<sid>/config_path` and reloads it for
  `shim delete`, rather than validating an unrelated default hypervisor.
  If that configuration no longer loads, recovery falls back to default
  configuration values and persisted state. Failure to record the path now
  fails sandbox startup
  ([#14152](https://github.com/kata-containers/kata-containers/pull/14152)).
- **Network teardown stays on its own thread.** Rust network cleanup no longer
  carries a network namespace guard across awaits on shared Tokio workers,
  preventing a worker from being left in the pod namespace
  ([#13886](https://github.com/kata-containers/kata-containers/pull/13886),
  [#13885](https://github.com/kata-containers/kata-containers/issues/13885)).
- **Failed passfd waits report an unknown exit.** Agent wait failures now produce
  exit status 255 and attempt normal stop and cleanup handling, instead of
  reporting success while leaving the process marked running
  ([#13963](https://github.com/kata-containers/kata-containers/pull/13963),
  [#13947](https://github.com/kata-containers/kata-containers/issues/13947)).
- **Container cleanup detaches its hotplugged devices.** `runtime-rs` tracks
  block and VFIO ownership per container, retains shared devices until the final
  detach, and keeps failed detach entries for retry. QEMU VFIO removal waits
  for deletion and tolerates devices already absent
  ([#13538](https://github.com/kata-containers/kata-containers/pull/13538)).
- **Explicit QEMU root ports are reserved first.** Automatic disk placement no
  longer consumes an address assigned to a VFIO root port, fixing startup with
  multiple extension disks and the NVIDIA SNP layout
  ([#14115](https://github.com/kata-containers/kata-containers/pull/14115)).

### Guest operation, storage and VM restore

- **Environment validation preserves whitespace.** Leading and trailing spaces
  and newlines remain intact in approved environment keys and values used by
  guest policy and hooks; delimiter and NUL validation remains in place.
  This fixes secrets whose values end with a newline
  ([#13933](https://github.com/kata-containers/kata-containers/pull/13933),
  [#13911](https://github.com/kata-containers/kata-containers/issues/13911)).
  Agent cache keys now include shared Rust sources and workspace manifests so
  those fixes invalidate cached agent binaries
  ([#14200](https://github.com/kata-containers/kata-containers/pull/14200)).
- **Ending a debug console session no longer stalls the agent.** The agent
  terminates the remaining shell and reaps it through the blocking pool,
  preventing a disconnected console from wedging a single-vCPU guest
  ([#14173](https://github.com/kata-containers/kata-containers/pull/14173),
  [#14230](https://github.com/kata-containers/kata-containers/issues/14230)).
- **Cloud Hypervisor opens merged EROFS images as flat VMDK.** The Rust backend
  writes the descriptor and enables backing files instead of treating the
  descriptor as raw data. Shared layout helpers and temporary-file tracking
  support cleanup; Cloud Hypervisor VM template tests drop their prior
  workarounds
  ([#14134](https://github.com/kata-containers/kata-containers/pull/14134),
  [#13788](https://github.com/kata-containers/kata-containers/pull/13788)).
  The agent also resolves virtio-mmio layer devices before mounting multi-layer
  EROFS ([#14305](https://github.com/kata-containers/kata-containers/pull/14305)).
- **EROFS image data is flushed before loop-device detach.** The image builder
  uses `conv=fsync` to avoid producing an empty data partition with an intact
  dm-verity hash. Rebuild custom images affected by this failure
  ([#14159](https://github.com/kata-containers/kata-containers/pull/14159)).
- **Dragonball preserves more device state across snapshots.** Restore retains
  block attachment layout, vsock port allocation and reset state, and KVM
  custom MSRs. Device state is saved before transport state, and template boot
  avoids capturing an established host upcall connection. The VMM exposes
  vsock reset controls, while the Rust runtime template path retains its
  no-reset policy. Snapshot restore remains an x86_64 path
  ([#14075](https://github.com/kata-containers/kata-containers/pull/14075)).

  <!-- Verify cross-version Dragonball snapshot compatibility before documenting
  reuse of templates created with an earlier release. -->

- **Packaged virtiofsd configurations stop forcing a thread pool.** Removing
  `--thread-pool-size=1` lets the Rust daemon use its no-pool default,
  avoiding requests completing outside snapshot synchronization and causing
  invalid handles or hangs after restore. Remove that argument from custom
  configurations that copied the packaged setting
  ([#14182](https://github.com/kata-containers/kata-containers/pull/14182)).

### Policies and deployment

The policy generator rebuilds additional groups from the final container
identity when container user or group settings override pod settings, while
retaining explicitly requested pod `supplementalGroups` and `fsGroup`.
A container-only user override preserves an explicit pod `runAsGroup`.
Pod-level `runAsGroup` without pod-level `runAsUser` is rejected before image
processing, matching CRI sandbox validation. Set the pod UID as well when
supplying a pod GID, and regenerate policies for affected workloads
([#14061](https://github.com/kata-containers/kata-containers/pull/14061)).

Repeated `kata-deploy` reconciliation preserves unchanged TOML and drop-in
contents and modification times, avoiding unnecessary CRI restarts, including
embedded containerd on k0s
([#14066](https://github.com/kata-containers/kata-containers/pull/14066),
[#14065](https://github.com/kata-containers/kata-containers/issues/14065)).
Empty TOML arrays remain `[]` instead of becoming `[""]`, including empty
annotation lists
([#14070](https://github.com/kata-containers/kata-containers/pull/14070),
[#14069](https://github.com/kata-containers/kata-containers/issues/14069)).
The installer's SELinux policy permits appending to CRI configuration files,
fixing CRI-O installation on enforcing hosts
([#14140](https://github.com/kata-containers/kata-containers/pull/14140),
[#14139](https://github.com/kata-containers/kata-containers/issues/14139)).

Devkit installations require `kata-ctl` in the deploy image and install it
under the host installation's `bin` directory, normally
`/opt/kata/bin/kata-ctl`. Custom amd64 and arm64 deploy images must include
its archive; the NVIDIA bundle now builds it too
([#14116](https://github.com/kata-containers/kata-containers/pull/14116),
[#14147](https://github.com/kata-containers/kata-containers/pull/14147)).

## Documentation

The composable-image design documents partition identity requirements and the
supported extension backends. The RuntimeClass guide explains the installed
devkit console client, and the new Substrate build and test guides describe
archive contents, image constraints and runtime verification.

Local build instructions use the separate `shim-v2-rust-tarball` and
`shim-v2-go-tarball` targets in place of `shim-v2-tarball`
([commit 39d38a5](https://github.com/kata-containers/kata-containers/commit/39d38a5dbe7ae6623a81380e6975b6de34919ab6)).
An agent-oriented contributor guide documents repository layout, validation
and runtime parity checks
([#13742](https://github.com/kata-containers/kata-containers/pull/13742)).

Maintainers gain an on-demand release-note drafting workflow with range
selection, spelling and formatting preflight checks and documentation
validation
([#14294](https://github.com/kata-containers/kata-containers/pull/14294),
[#14323](https://github.com/kata-containers/kata-containers/pull/14323),

## Upgrading

1. Follow the [installation guide](../installation.md) and move host containerd
   to 2.3 or later. Replace any `kata-manager` automation.
2. Validate custom virtio-blk rootfs partition identities and keep them distinct
   from extension identities. Rebuild images affected by the EROFS flush bug.
3. Roll out matching host runtime and guest assets, then recreate sandboxes
   that need the updated agent, kernel or guest libraries. Review custom
   `virtiofsd` arguments and remove `--thread-pool-size=1` where copied.
4. Regenerate policies with this release. Check container identity overrides,
   set pod `runAsUser` alongside pod `runAsGroup`, and review workloads
   affected by directory masking and now-enforced PID limits.
5. Update custom agent clients for removal of `RemoveContainerRequest.timeout`
   and review any dependence on early timeout responses.
6. Include the `kata-ctl` archive in custom devkit deploy images. For Substrate,
   use the dedicated guest archive and create fresh snapshots when replacing
   its image.

See [Upgrading](../Upgrading.md) for general guidance and the
[breaking changes](#breaking-changes) and [known issues](#known-issues) above.
