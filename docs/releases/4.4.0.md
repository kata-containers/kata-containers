# Kata Containers 4.4.0

4.4.0 follows [4.3.1](4.3.1.md), with compressed
EROFS guest disks, a dedicated Substrate guest, larger Cloud Hypervisor
sandboxes, and improvements to recovery after shim and VMM failures.

## New features

### A dedicated Substrate guest

The build and release definitions add
`kata-static-substrate-VERSION-ARCH.tar.zst` for amd64 and arm64. It contains
a Debian `trixie-slim` guest and the standard Kata kernel; Substrate supplies
its host binaries. The guest uses a separate GNU libc agent as PID 1, with
seccomp enabled and agent policy, init-data and dm-verity support disabled.
It remains separate from the regular Kata archives and `kata-deploy` downloads
([#14223](https://github.com/kata-containers/kata-containers/pull/14223)).

This guest uses ext4 for Substrate's PMEM/DAX mounts, retains package metadata
for inspection, and omits general-purpose guest tools such as iptables and
`mkfs.ext4`. It has no chrony service: use a VMM that corrects the clock after
restore, and create fresh snapshots when changing the guest image. See the
[build instructions](../../tools/osbuilder/README.md) and
[Substrate test guide](../../tests/integration/substrate/README.md).
The upstream boot measurements do not establish performance gains for this build.

### Cloud Hypervisor supports up to 512 vCPUs on x86_64 KVM

Both runtimes raise the Cloud Hypervisor limit to 512 vCPUs on x86_64 KVM,
with matching guest kernel capacity and resize validation. MSHV and other
architectures retain the 256-vCPU Cloud Hypervisor limit. Host CPU limits and
configuration adjustment still apply; this is a supported upper bound, not
a new default VM size
([#13811](https://github.com/kata-containers/kata-containers/pull/13811)).

### Rootless VFIO-AP on s390x

`runtime-rs` recognizes VFIO-AP mediated devices through
`/dev/vfio/devices/vfioN` and supports IOMMUFD descriptor passing for cold-plug.
The s390x QEMU build enables IOMMUFD, and functional coverage includes rootless
cold-plug and a negative rootless hot-plug case. The TEE Helm example enables
rootless mode for the Secure Execution Rust handler; the runtime template
continues to default to `rootless = false`
([#14145](https://github.com/kata-containers/kata-containers/pull/14145)).

### Additional guest and firmware support

- Cloud Hypervisor in `runtime-rs` uses VMDK for multi-layer EROFS container
  images, allowing the VM template tests to use their standard workloads
  ([#14134](https://github.com/kata-containers/kata-containers/pull/14134)).
- The agent resolves virtio-mmio devices for multi-layer EROFS mounts
  ([#14305](https://github.com/kata-containers/kata-containers/pull/14305)).
  This does not add Firecracker support for the combined VMDK format.
- The amd64 Rust release archive gains `td-shim` firmware at
  `/opt/kata/share/td-shim/td-shim.bin`. This packages firmware for Dragonball;
  it does not establish general TDX support for other handlers
  ([#14114](https://github.com/kata-containers/kata-containers/pull/14114),
  [#14347](https://github.com/kata-containers/kata-containers/pull/14347)).

## Breaking changes

### Standard guest disks switch to compressed EROFS

The regular guest disk image builds and both runtimes' generated defaults
switch from ext4 to EROFS. The Substrate image is an explicit ext4 exception.
Systemd guests get temporary writable storage at `/var/lib/systemd`; its state
is discarded when the VM stops. Guest disk format is independent of the
container snapshotter: this change does not require selecting the EROFS
snapshotter
([#14187](https://github.com/kata-containers/kata-containers/pull/14187)).

When retaining custom configurations, match `rootfs_type` to the image you
actually deploy. For an EROFS QEMU image, set `rootfs_type = "erofs"` and
`disable_image_nvdimm = true`. In `runtime-rs`, also use
`vm_rootfs_driver = "virtio-blk-pci"`, or `virtio-blk-ccw` on s390x. The
new generated configurations already select these settings. Keep an explicit
`rootfs_type = "ext4"` when retaining an ext4 image. See the
[image builder guide](../../tools/osbuilder/image-builder/README.md).

For `runtime-rs` QEMU, Cloud Hypervisor and Dragonball virtio-blk boot paths,
root partition selection now uses `PARTUUID`, preventing an extension disk
that probes first from becoming the guest root. Custom images need root data
in partition 1 and, when measured, verity hashes in partition 2. DOS images
need a nonzero disk signature; GPT images use partition GUIDs. Rootfs and
extension images must have distinct partition identities. Initrd and PMEM
boot paths retain their existing selection
([#14161](https://github.com/kata-containers/kata-containers/pull/14161)).

### Firecracker reserves read-only disk slots

Both runtimes now honor device-level read-only requests using separate
Firecracker placeholder drives. Set `block_device_read_only_slots` before
creating a sandbox: the default is `1`, leaving seven writable attachment
slots and one read-only slot, separate from the guest OS root disk. Values
from 0 through 7 are accepted; `0` disables read-only attachments. Exhausting
either pool fails the attachment, without borrowing from the other pool.
Container root disks and read-only image devices consume these slots too.
https://github.com/kata-containers/kata-containers/security/advisories/GHSA-hjjf-cq78-fj3h
 has details on the motivation for this change.

Recreate affected sandboxes: upgrading cannot change the mode negotiated by
an existing VMM disk. Older saved Go sandboxes restore with zero read-only
slots and reject new read-only attachments until recreated. The Rust pool
grows from five to eight slots. On x86_64 with Firecracker v1.17.0, one guest
OS root disk and one vsock device, that leaves capacity for seven NICs rather
than ten; an eighth NIC prevents startup.

Mixed access modes for the same shared block device remain unsupported:
reuse retains the first attachment's mode, without rejecting mode conflicts.
This mechanism does not translate OCI `root.readonly` into device-level
protection. See the [Firecracker limits](../how-to/firecracker-read-only-block-devices.md).

### Runtime and deployment contracts

- **The containerd minimum is 2.3.** The latest CI selection remains 2.4.
  Upgrade the host daemon separately; installing Kata does not upgrade it
  ([#14183](https://github.com/kata-containers/kata-containers/pull/14183)).
- **Requested core scheduling must succeed.** When containerd supplies a
  nonempty `SCHED_CORE`, the Rust shim now fails startup if it cannot activate
  core scheduling, instead of starting without the requested isolation.
  Check host support and the reported error before retrying; unset or empty
  `SCHED_CORE` still leaves it disabled
  ([#14204](https://github.com/kata-containers/kata-containers/pull/14204),
  fixes [#14174](https://github.com/kata-containers/kata-containers/issues/14174)).
- **Container removal waits synchronously.** The agent ignores the former
  `RemoveContainerRequest.timeout`; the protocol reserves its field number
  and name, and `runtime-rs` stops sending it. Custom clients must not rely on
  that field to bound guest cleanup
  ([#14146](https://github.com/kata-containers/kata-containers/pull/14146)).
- **`kata-manager` is retired.** It prints a notice and exits with failure.
  Replace automation invoking it with a supported method from the
  [installation guide](../install/README.md)
  ([#14265](https://github.com/kata-containers/kata-containers/pull/14265)).

## Notable fixes

### Recovery and resource cleanup

`runtime-rs` writes `state.json` atomically under `/run/kata/<sandbox-id>`,
records resources during setup, and retains state until cleanup completes.
Recovery records the sandbox configuration path and `keep_abnormal` decision,
restores rootless cleanup correctly, releases init-data images and block
emptyDir disks, restores passed-through NIC drivers, and removes Kata-created
network links and pinned namespaces. Failed cleanup keeps state for retry;
`keep_abnormal` deliberately preserves it for debugging
([#14162](https://github.com/kata-containers/kata-containers/pull/14162),
related [#14112](https://github.com/kata-containers/kata-containers/issues/14112)).

Network work runs on dedicated threads without blocking Tokio workers or
leaving them inside a pod namespace. Partial attachment can resume, and
cleanup tolerates namespaces and cgroups already removed by the container
manager
([#13886](https://github.com/kata-containers/kata-containers/pull/13886),
[#14370](https://github.com/kata-containers/kata-containers/pull/14370)).
The inherited shim listener is closed on exec so a surviving VMM cannot keep
a dead shim's socket accepting unanswered requests. Stale sockets no longer
prevent retrying a failed start
([#14128](https://github.com/kata-containers/kata-containers/pull/14128),
[#14143](https://github.com/kata-containers/kata-containers/pull/14143)).

Failed agent health checks now stop the sandbox and notify waiters. Failed
passfd waits report unknown exit status `255` and attempt cleanup, rather than
reporting success. Late subscribers retain sandbox exit notifications
([#13967](https://github.com/kata-containers/kata-containers/pull/13967),
[#13963](https://github.com/kata-containers/kata-containers/pull/13963),
[#13919](https://github.com/kata-containers/kata-containers/pull/13919)).

Container teardown detaches its hotplugged devices, retains shared devices
until their final detach, and supports repeated VFIO hot-unplug
([#13538](https://github.com/kata-containers/kata-containers/pull/13538)).
Copied-volume watchers are tracked per container, so removing one user does
not stop another's updates. Closing inotify descriptors runs off the async
workers to avoid hanging a shim with multiple watched volumes
([#13962](https://github.com/kata-containers/kata-containers/pull/13962),
[#14379](https://github.com/kata-containers/kata-containers/pull/14379),
fixes [#13641](https://github.com/kata-containers/kata-containers/issues/13641)).

### Agent, policy and workload behavior

- Directory entries in OCI `maskedPaths` are now hidden with a shared
  read-only tmpfs, including nested paths and SELinux mount labels. Paths such
  as `/sys/firmware` that previously remained visible are now masked as
  requested. Review workloads that depended on that visibility
  ([#14189](https://github.com/kata-containers/kata-containers/pull/14189)).
- PID limits survive protocol conversion and reach container cgroups
  ([#14141](https://github.com/kata-containers/kata-containers/pull/14141)).
- Environment validation preserves approved whitespace, including trailing
  newlines in secrets, instead of trimming bytes
  ([#13933](https://github.com/kata-containers/kata-containers/pull/13933),
  fixes [#13911](https://github.com/kata-containers/kata-containers/issues/13911)).
- Generated policies preserve an explicit pod group when only the container
  user changes and replace inherited primary groups when both are overridden,
  while retaining requested supplemental groups and `fsGroup`. Pod-level
  `runAsGroup` without `runAsUser` is rejected: add the pod user explicitly
  ([#14061](https://github.com/kata-containers/kata-containers/pull/14061)).
- Removal policy permits cleanup after a failed create that never established
  policy state. The agent also removes resources when no container object was
  created and avoids a hotplug-timeout cleanup panic
  ([#14270](https://github.com/kata-containers/kata-containers/pull/14270),
  [#14281](https://github.com/kata-containers/kata-containers/pull/14281)).
- Exclusive-CPU sandboxes with negative CPU quota use CPU shares for initial
  sizing, preventing statically sized Guaranteed pods from being stuck at one
  vCPU. Zero or absent quota does not trigger this fallback
  ([#14244](https://github.com/kata-containers/kata-containers/pull/14244)).
  The Go runtime also parses current and deprecated CRI-O pod resource
  annotations for sandbox sizing
  ([#13649](https://github.com/kata-containers/kata-containers/pull/13649)).
- Debug console disconnects kill and reap the shell without blocking the
  agent. Mem-agent initializes memory-cgroup support only when enabled,
  mounts `debugfs` when needed, and survives cancelled command responses
  ([#14173](https://github.com/kata-containers/kata-containers/pull/14173),
  [#14232](https://github.com/kata-containers/kata-containers/pull/14232)).
- Bind sources such as `/data/proc/train` are shared correctly: only `/proc`,
  `/sys` and their descendants count as system mounts
  ([#14194](https://github.com/kata-containers/kata-containers/pull/14194)).

### Images, deployment and VM templates

EROFS image assembly writes directly at the partition offset and verifies the
result, avoiding loop-device races that could publish blank root partitions.
Builds reject missing verity hash partitions, and extension hash validation
also runs for unmeasured base images
([#14373](https://github.com/kata-containers/kata-containers/pull/14373),
[#14123](https://github.com/kata-containers/kata-containers/pull/14123)).
Agent cache keys include shared Rust sources, preventing stale agents after
library fixes
([#14200](https://github.com/kata-containers/kata-containers/pull/14200)).

`kata-deploy` preserves unchanged CRI file timestamps, avoiding unnecessary
restarts during reconciliation, preserves empty TOML arrays, and permits CRI-O
configuration appends under SELinux enforcement
([#14066](https://github.com/kata-containers/kata-containers/pull/14066),
[#14070](https://github.com/kata-containers/kata-containers/pull/14070),
[#14140](https://github.com/kata-containers/kata-containers/pull/14140)).
Devkit installations require `kata-ctl`, now included in the NVIDIA bundle
([#14116](https://github.com/kata-containers/kata-containers/pull/14116),
[#14147](https://github.com/kata-containers/kata-containers/pull/14147)).

Dragonball restores block-device layout, vsock port allocation and reset state,
and KVM paravirtual MSRs in the required order. Template startup omits the host
upcall connection. Both runtimes drop the default virtiofsd thread pool, avoiding
requests racing saved device state
([#14075](https://github.com/kata-containers/kata-containers/pull/14075),
[#14182](https://github.com/kata-containers/kata-containers/pull/14182)).
QEMU emits explicitly addressed PCIe root ports before automatically placed
devices, preventing extension disks from occupying GPU slots
([#14115](https://github.com/kata-containers/kata-containers/pull/14115)).

## Security

Dragonball's virtio-PCI transport rejects queue reconfiguration after device
activation and prevents status-bit clearing from reopening that window.
See https://github.com/kata-containers/kata-containers/security/advisories/GHSA-958x-8rq9-832p for more details.

Dependency updates include Cloud Hypervisor's published virtio-pmem shutdown
use-after-free fix
([#14345](https://github.com/kata-containers/kata-containers/pull/14345),
[upstream advisory](https://github.com/cloud-hypervisor/cloud-hypervisor/security/advisories/GHSA-3r3x-6hgg-2m38)),
Tokio's RUSTSEC-2026-0386 correction
([#14384](https://github.com/kata-containers/kata-containers/pull/14384)),
and Rust certificate and compression updates
([#14315](https://github.com/kata-containers/kata-containers/pull/14315)).
The latter also updates Go networking dependencies for GO-2026-6860 and
GO-2026-6866, and the runtime's compression library for GO-2026-6865.

## Known issues

- Firecracker still cannot interpret the VMDK layout combining multiple EROFS
  container layers. Reserving additional read-only slots does not enable it.
  Shared block devices also retain the first attachment's access mode; see
  [the documented limits](../how-to/firecracker-read-only-block-devices.md).
- The compression updates leave the older `zstd` 0.11.2 / `zstd-safe` 5.0.2
  dependency pulled in by Dragonball's `nydus-utils` unchanged. The update
  explicitly does not resolve that dependency chain
  ([commit](https://github.com/kata-containers/kata-containers/commit/6d086cf784ca5bbee9a1d8928957d6668f027c2d)).
- An OpenVMM launch-failure regression test is disabled as flaky
  ([#14252](https://github.com/kata-containers/kata-containers/pull/14252),
  [#14228](https://github.com/kata-containers/kata-containers/issues/14228)).

## Upgrading

1. Upgrade containerd hosts to 2.3 or later before deploying this release.
2. Merge the generated configuration changes with local overrides. Match
   `rootfs_type` to each image, select block attachment for EROFS QEMU guests,
   and verify partition identities for custom Rust virtio-blk images.
3. Budget Firecracker's separate read-only and writable pools before creating
   sandboxes. Check the seven-NIC x86_64 limit for the documented device layout
   and avoid mixed access modes for a shared device.
4. Regenerate agent policies. Set pod `runAsUser` when using pod `runAsGroup`,
   validate overridden identities, and account for synchronous removal.
5. Check hosts where containerd requests core scheduling: an activation failure
   now prevents Rust shim startup. Review workloads that read paths now hidden
   by OCI directory masking or exceed their configured PID limits.
6. Replace `kata-manager` automation, update custom CDH key provider file
   references, and review Trustee image repository changes if mirroring images.
7. For Substrate guest updates, create fresh snapshots and ensure the VMM
   corrects the clock on restore.

See [Upgrading](../Upgrading.md) and the
[installation guide](../install/README.md) for deployment procedures.
